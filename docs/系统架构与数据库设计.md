# 网络故障工单系统 — 系统架构与数据库设计

## 一、项目概述

### 1.1 项目背景

本项目为《互联网应用开发实践》课程设计，选题为 **网络故障工单系统**。系统面向网络工程领域的故障管理场景，实现故障报修、工单流转、指派处理、评论回复、数据统计等核心功能。

### 1.2 项目定位

| 阶段 | 目标 | 时间 |
|------|------|------|
| **课设（当前）** | 核心功能跑通：用户系统 + 工单CRUD + 状态流转 + 指派 + 评论 + 统计面板 + 搜索筛选 | 2周 |
| **毕业设计（后续）** | + 智能故障分类 + 网络拓扑可视化 + 知识库 + 实时告警 + 数据分析报表 + 移动端适配 | 后续迭代 |

### 1.3 应用场景

- **网络运维团队**：日常故障报修、工单跟踪、处理记录
- **IT服务台**：用户提交故障、运维人员接单处理、管理员监督统计
- **网络工程项目**：贴合网络工程专业方向，解决实际运维管理问题

## 四、工单状态流转

```
                    ┌─────────────┐
                    │   待处理     │
                    │  (pending)  │
                    └──────┬──────┘
                           │ 管理员指派 / 运维接单
                           ▼
                    ┌─────────────┐
                    │   处理中     │
                    │ (processing)│
                    └──────┬──────┘
                           │ 运维标记完成
                           ▼
                    ┌─────────────┐
                    │   已完成     │
                    │ (completed) │
                    └──────┬──────┘
                           │ 管理员/创建人关闭
                           ▼
                    ┌─────────────┐
                    │   已关闭     │
                    │  (closed)   │
                    └─────────────┘
```

**状态流转规则：**

| 当前状态 | 可转换为 | 操作角色 |
|---------|---------|---------|
| 待处理 | 处理中 | 管理员（指派）、运维人员（接单） |
| 待处理 | 已关闭 | 管理员、创建人 |
| 处理中 | 已完成 | 处理人（运维人员） |
| 处理中 | 已关闭 | 管理员 |
| 已完成 | 已关闭 | 管理员、创建人 |
| 已关闭 | — | 终态，不可转换 |

## 九、后端详细设计

### 9.1 分层架构

```
请求 → Controller → Service → Mapper → 数据库
         ↓            ↓          ↓
      参数校验     业务逻辑    SQL操作
      返回响应     事务管理    MyBatis-Plus
```

| 层 | 职责 | 示例 |
|------|------|------|
| Controller | 接收请求、参数校验、调用Service、返回统一响应 | `TicketController.java` |
| Service | 业务逻辑、事务管理、权限判断 | `TicketService.java` |
| Mapper | 数据库操作，继承 MyBatis-Plus 的 BaseMapper | `TicketMapper.java` |
| Domain | 实体类、DTO、VO、Query | `Ticket.java`, `TicketDTO.java` |
| Common | 统一响应体、全局异常处理、常量 | `Result.java`, `GlobalExceptionHandler.java` |

### 9.2 统一响应格式

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { ... }
}
```

### 9.3 全局异常处理

| 异常类型 | 处理方式 |
|---------|---------|
| 参数校验失败 | 返回 400 + 具体字段错误信息 |
| 未登录/Token过期 | 返回 401 |
| 无权限 | 返回 403 |
| 业务异常 | 返回对应业务错误码和信息 |
| 系统异常 | 返回 500 + 记录日志 |

## 十一、设计决策记录

### 11.1 为什么选择前后端分离 + Monorepo

- 前端用 VSCode 开发，后端用 IDEA 开发，各自独立
- 统一放在一个 Git 仓库，版本管理更完整，答辩时一眼看全貌
- 跟之前差旅报销项目结构一致，已有经验

### 11.2 为什么预留操作日志表

- 课设阶段核心功能优先，操作日志可选实现
- 毕业设计阶段需要审计追踪功能，提前设计好表结构避免后期改库
- 体现"为毕业设计预留扩展点"的设计思路

### 11.3 密码加密方案

- 使用 BCrypt 加密存储密码，不存明文
- Spring Security 提供 BCryptPasswordEncoder，集成简单

### 11.4 认证方案

- JWT (JSON Web Token) 无状态认证
- 前端登录后存储 Token，每次请求通过 Axios 拦截器自动携带
- 后端通过拦截器校验 Token 有效性
